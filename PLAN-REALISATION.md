## 1. Décisions de cadrage

### 1.1 Pile technique imposée

| Couche | Technologie | Précisions retenues |
|---|---|---|
| Frontend (site public + back office + espaces partenaires) | **React** | Vite 8 + React 19 + TypeScript (oxlint, Prettier, Vitest), React Router, TanStack Query, Zustand, React Hook Form + Zod, Axios, Ant Design (thème aux couleurs de la charte), i18next (fr / en) |
| Backend | **Laravel** (API REST seule, aucune vue Blade métier) | Laravel 13, PHP 8.3, JWT (`php-open-source-saver/jwt-auth`, comme décidé sur Mon Gravier), API Resources, Form Requests, Policies, files d'attente + planificateur |
| Mobile | **Flutter** | Monorepo (melos) : paquets partagés `core`, `api_client`, `ui` + une application par profil ; Riverpod, dio, flutter_secure_storage, drift (hors ligne agent), FCM |
| Base de données | **PostgreSQL** 15+ | Extension `btree_gist` : contrainte d'exclusion sur les périodes de séjour (anti-surbooking garanti par la base) ; `numeric` pour tous les montants ; séquences dédiées aux numérotations |

### 1.2 Charte graphique

| Rôle | Couleur | Jeton | Usage |
|---|---|---|---|
| Principale | `#1E3A5F` Bleu nuit | `--color-primary` | Navigation, boutons principaux, titres, liens |
| Secondaire | `#D9C3A5` Sable | `--color-secondary` | Cartes, accents, éléments décoratifs, survols, badges |
| Fond | `#F8F7F4` Blanc cassé | `--color-bg` | Arrière-plans, espaces |

Règles : texte bleu nuit sur blanc cassé ou sur sable (contraste suffisant) ; **jamais de texte sable sur fond clair** (illisible) ; le sable sert de surface, pas de couleur de texte. Couleurs sémantiques à dériver (succès, alerte, erreur, information) et palette de 8 états pour le planning (libre, réservé, occupé, départ du jour, en ménage, en maintenance, bloqué propriétaire, « Occupée »). Les mêmes jetons alimentent le thème Ant Design (web) et le `ThemeData` Flutter (mobile).

### 1.3 Principes d'architecture (leçons de Mon Gravier)

| À reprendre | À ne pas reproduire |
|---|---|
| Profils cloisonnés, un utilisateur = un profil | Deux backends (`graviers` Blade + `apigravier`) avec logique métier dupliquée et divergente → **ici, UNE seule API Laravel** sert web et mobile |
| Double validation + circuit de preuve (`Traits/DoubleValidationPaiement.php`) | Jeton = identifiant chiffré non expirable, passé dans le corps → **JWT expirable en en-tête `Authorization`** |
| Paiement en ligne PaySecure : init, webhook idempotent, re-vérification serveur à serveur (`PaiementEnLigne.php`) | HTTP 200 partout avec code dans le corps, `getMessage()` exposé → **vrais codes HTTP + enveloppe unique** |
| `Services/FneService.php` (facture normalisée DGI) | `Help.php` fourre-tout de ~950 lignes → **Services par domaine, testés** |
| Prix, disponibilité et taxes calculés **uniquement** côté serveur | Trois apps Flutter copiées-collées (~70 % identiques) → **monorepo à paquets partagés** |
| Exports Excel / Word / PDF avec filtre de période, règles de listes | Pas de Git, pas de recette, déploiement fichier par fichier → **Git + recette + déploiement scripté dès P0** |
| Module écritures comptables déjà cadré (`PLAN-module-ecritures-comptables.md`) | Jeton mobile en clair dans SharedPreferences → **flutter_secure_storage** |
| Apps Flutter : structure `screens/<fonction>/components/`, messages d'erreur réseau en langage clair, onglets vivants (`IndexedStack`), corpus de tests en français | ~95 appels `http.post` écrits à la main dans les écrans, état en variables globales (`globale.dart`, 862 lignes) → **client API unique (dio + intercepteurs), dépôts de données, Riverpod** |
| Retour de paiement par lien profond (`gravier://ouvrir`), URL de passerelle fournie par l'API | Total recalculé dans l'app avec **repli silencieux** si le serveur ne répond pas (écart réel constaté : 443 F affichés, 437 F facturés) → **l'app n'affiche que le montant renvoyé par le serveur, sinon elle bloque** |
| Notices de déploiement, journaux de lots, manuel utilisateur, cahier de recette | Environnement en constante compilée (`const env = 'prod'`), APK de production **signés avec la clé de debug**, permission `QUERY_ALL_PACKAGES`, iOS jamais configuré → **flavors dev / recette / prod, keystore de release, publication store possible dès le lot 2** |
| Journal d'audit automatique par middleware, écrit après la réponse, champs sensibles exclus, récit en langage clair (`Audit::recit()`) | Contrôleurs de 5 000 à 7 000 lignes, 9 Form Requests pour 553 routes, services 100 % statiques, aucune Policy (profil = entier comparé en dur) → **contrôleurs minces, une Form Request par écriture, services injectés, Policies issues de la matrice profils × actions** |
| Principe écrit dans le code : « masquer une entrée de menu n'est pas une protection » — le refus se fait sur la route | Code de livraison stocké en clair et protégé seulement par son absence des vues → **codes d'arrivée / de prise en charge / de livraison chiffrés en base, jamais sérialisés vers les profils agent, chauffeur, livreur et back office ; vérification par comparaison côté serveur** |
| Certification FNE non bloquante, écriture comptable déclenchée à la certification, commandes de rattrapage | `QUEUE_CONNECTION=sync` : courriels, DGI et passerelle dans la requête HTTP (un délai DGI = page blanche) → **file d'attente + worker dès le lot 1** |
| Schéma des écritures comptables (identifiant stable, contre-passation, table d'anomalies) | Migrations non rejouables (base reconstruite par dump SQL), table `configuration` à ligne unique de ~60 colonnes → **migrations propres rejouables depuis zéro, paramètres clé / valeur typés et historisés** |
| Commentaires de code denses, en français, qui expliquent le pourquoi ; tests nommés par règle métier | Tests exécutés sur la base de développement, tests qui lisent le source des vues, aucune intégration continue → **base PostgreSQL de test isolée, tests de comportement, CI obligatoire** |
| Filtre de période `?du=&au=` sur toutes les listes | Filtre réécrit dans chaque contrôleur, parfois appliqué en PHP après chargement de toute la table ; export Excel présent sur 2 écrans seulement, Word sans bibliothèque → **composant de liste unique : filtre en SQL, exports Excel (maatwebsite/excel), Word (phpoffice/phpword) et PDF (dompdf) génériques** |
| — | Secrets réels dans le dépôt (`.env`, mot de passe SMTP dans `.env.example` et `config/constantes.php`), `APP_DEBUG=true` → **aucun secret versionné, contrôle automatique en CI** |
| — | Dépendances mortes ou en triple (3 paniers, 4 bibliothèques de notifications, permissions installées mais inutilisées), SMS et push inexistants → **une bibliothèque par besoin ; SMS et push sont des développements neufs, pas des portages** |
| Test de charge k6 avec profil « fumée » | Aucune notification push, aucun mode hors ligne, tous les libellés en dur en français → **FCM, base locale pour l'agent, fichiers `.arb` fr / en dès le premier écran** |

## Décisions à prendre (CdC § 13.4) — avec recommandation

- [ ] D1 — Vente par logement nommé ou par type ? → **Les deux, réglage par résidence** (déjà prévu au § 7.1) ; défaut : logement nommé.
- [ ] D2 — Rémunération des propriétaires au démarrage ? → **Prix négocié + prix de vente administrateur** (mode par défaut du CdC) ; le mode commission reste disponible sur le mandat.
- [ ] D3 — Taxe de séjour par commune ? → À obtenir du fiscaliste (P0-CAD-07) ; table `taxes_sejour_communes` paramétrable, à 0 par défaut.
- [ ] D4 — Caution : encaissement ou empreinte carte ? → **Encaissement systématique au lot 2**, empreinte ajoutée si la passerelle retenue la propose.
- [ ] D5 — Canaux externes dès le lot 1 ? → **Non : lot 4**, mais la réservation manuelle « canal externe » existe dès le lot 1 et le modèle de données est prêt.
- [ ] D6 — Repas : partenaires, cuisine interne, ou les deux ? Livreurs dédiés ou chauffeurs polyvalents ? → **Les deux** (restaurateur interne = même circuit) ; **un compte peut cumuler chauffeur et livreur** dans une même application « Courses ».
- [ ] D7 — Validation des publications : un administrateur ou un validateur désigné ? → **Validateur désigné dans les Paramètres**, avec la règle « jamais sa propre saisie ».
- [ ] D8 — Nom commercial, domaine, charte ? → Palette arrêtée (bleu nuit / sable / blanc cassé) ; **nom, domaine et logo restent à fournir**.
- [ ] D9 — Nombre d'applications mobiles : le CdC en annonce six mais regroupe « Chauffeur / Livreur / Apporteur » → **six applications** : Client, Agent, Propriétaire, Courses (chauffeur + livreur), Apporteur, Restaurateur — le monorepo rend ce découpage modifiable sans réécriture.
- [ ] D10 — Rendu du site public : application React pure avec pré-rendu, ou rendu serveur (Next.js) si un VPS est retenu → à décider avec P0-ENV-02, car le référencement du catalogue en dépend.
- [ ] D11 — Transmission DGI (facture normalisée électronique, P1-FNE-01) : la table `facture` de Mon Gravier porte une colonne `numero_fne`, mais **aucun code de transmission à la DGI n'existe dans le projet de référence** (vérifié dans `apigravier` et confirmé par l'audit complet du 13/04/2026, qui recense 89 défauts sans jamais mentionner FNE ni DGI) → il n'y a rien à porter. Il faut soit un accès réel à l'API du prestataire agréé DGI retenu (identifiants, documentation), soit la décision explicite de reporter la certification fiscale (facture interne non normalisée en attendant). Concerne le back-office uniquement (facturation), pas le site public ni le mobile.
- [ ] D12 — Prestataire SMS (P1-NOT-02) : le CdC ne désigne aucun fournisseur (« développement neuf, absent de Mon Gravier ») → l'infrastructure est prête (passerelle HTTP générique, URL et noms de champs paramétrables dans `config/notifications.php`) mais fonctionne pour l'instant en passerelle d'essai (journal seulement, rien n'est réellement envoyé). Il faut le prestataire retenu et ses identifiants pour activer l'envoi réel — même situation que PaySecure pour le paiement en ligne.
- [ ] D13 — Seuil de signalement « tarif hors médiane » (P1-TAR-05) : le CdC demande que les écarts soient signalés sans donner de pourcentage → **30 % par défaut**, réglable dans les Paramètres (`proprietaires.ecart_mediane_seuil`) sans déploiement.

## Risques principaux

| Risque | Parade |
|---|---|
| PostgreSQL, files d'attente ou cron indisponibles sur l'hébergement mutualisé | Vérification en P0-ENV-02 ; VPS dès le départ si nécessaire |
| Capacité de l'hébergement mutualisé (Mon Gravier coupé par l'hébergeur à 100–150 visiteurs) | VPS dès la production, test k6 en profil « fumée » puis complet **avec accord de l'hébergeur**, limitation de débit compatible avec des mobiles derrière un même NAT |
| Double vente (direct + canaux) | Contrainte d'exclusion en base + blocage bidirectionnel + alerte de conflit |
| Erreur de calcul fiscal (TVA, TDT, taxe de séjour, retenues) | Formules validées par le fiscaliste en P0, cas chiffrés transformés en tests, contrôle de cohérence |
| Régression financière (caisse, soldes) | Logique dans des Services testés, jamais dans les contrôleurs ni dans React / Flutter ; audit systématique |
| Portage de code Mon Gravier écrit pour MySQL | Revue des requêtes brutes, types et fonctions de date lors du portage vers PostgreSQL |
